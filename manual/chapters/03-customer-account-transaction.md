# 03｜客户、账户与交易

### 先把调查对象分清楚

客户是自然人或机构；账户属于客户；交易发生在账户上，并与交易对手发生联系。一个客户可以有多个账户，同一个交易对手也可能出现在不同客户的交易里。若把这些概念塞进一张宽表，重复信息会使关系难以验证。

RiskCase 的账户没有余额、借贷分录或付款状态机。这里保存的是调查所需的掩码账号、账户类型、币种、开户日期与状态。

### 对象关系如何形成图

[figure: 03-investigation-entities.svg]

客户与账户是持久化关系；交易引用账户与对手方；风险告警关联客户、账户、信号和交易；案件则围绕告警管理调查生命周期。每条边都回答一个业务问题：谁的账户、哪笔交易、该信号关联什么。

### 账户不等于账本

<!-- page -->

[source: backend/RiskCase.Domain/Entities/Account.cs#public static Account Create|17]

账户实体限制格式和调查所需字段，并以 `CustomerId` 表达所有权。交易实体记录方向、金额、币种、发生时间、渠道和对手方引用。金额是历史观察值，不是可用于结算的余额变更。

这种建模让风险工作区能做证据汇总，而不承担银行核心账务职责。

### 跨账户线索如何被调查

<!-- page -->

**已知**：Aroha 与 Mateo 各有自己的有效账户。Aroha 的 TX-1、TX-2 指向 CP-X，Mateo 的 TX-3 也指向 CP-X。主告警仍以 Aroha 和她的账户为主体。

1. 在来源交易中读取各自 AccountId，通过账户找到实际客户；不能将所有交易强行标为主客户所有。
2. Presenter 为两名客户和两个账户各建立稳定节点，再为三条交易分别建立节点。CP-X 按 CounterpartyReference 合并为一个对手方节点。
3. 图中的路径说明两客户都与同一对手有观察交易。核查交易时间和经营用途后，才能决定它是正常共同商户还是值得深查的线索。

**判读**：可以重建“谁的哪条观察连接到谁”，仍不能推导双方相识、共同控制或资金违法。账号在 UI 掩码展示，交易金额是历史观察，不是可写余额。

### 练习与本章小结

<!-- page -->

**练习**

1. 为什么交易和账户需要分开的实体？
2. 共享对手方是一条怎样的事实，哪些结论仍然未知？
3. 如果产品加入余额和冻结逻辑，为什么已经跨出了当前模型边界？

**参考解**

1. 账户是长期对象，交易是带时间、金额和引用的一次观察。一账户有多笔交易，一告警也可能引用其他客户有效账户的交易，不能把两者压成一行。
2. 共同对手方是可复核的图路径。尚不知道两客户是否相识、谁控制资金、交易是否合法；商户可能服务许多互不相关客户。
3. 余额、冻结和资金划转需要账务一致性、额度与外部执行授权，当前模型只读观察记录，无法靠新增一个按钮满足这些约束。

**小结**：客户、账户、交易是不同层次的调查对象。交易历史可读；账户余额与资金操作不属于 RiskCase。
