# 02｜理解银行风险告警

### 告警是一个有来源的业务事件

同一笔交易可能被不同上游规则发现。若只保存一句“高风险”，调查员无法追问谁发现、何时发现、依据什么。RiskAlert 因此保留外部告警编号、来源系统、检测时间、类别、严重度、可选分数、信号和交易引用。

外部编号用于识别来源事件；RiskCase 是内部调查工作项。两者有关联，但不应混为一体：一个描述“上游发现了什么”，另一个记录“银行如何调查”。

处理顺序很重要：API 先检查摄入密钥，应用验证通过后，幂等存储开始事务并锁定 scope/key。只有新意图才调用 Handler，规范化来源身份并取得第二把业务身份锁；业务资料、审计与回执最终一起提交。重复投递是网络系统的常态，不应悄悄生成两份案件。

### 传输重复与业务重复的区别

<!-- page -->

**已知**：来源 Monitor-A、外部编号 AL-42、载荷 P。上游收到超时后，不知道案件是否已经提交。下表是假设性机制推演，P′ 表示风险分数等业务字段已改变。

| 后续请求 | 当前实现如何判断 |
|---|---|
| 原键 K、原载荷 P | 在用户/上游 scope 内读取 K 的回执；已成功则返回原结果，不执行第二次业务写入。 |
| 新键 K2、原载荷 P | 进入 Handler 后锁定来源身份；发现已有同内容告警，返回已有案件，并为 K2 保存结果。 |
| 新键 K3、载荷 P′ | 来源身份相同但内容不同，409 external_alert_payload_conflict；不覆盖告警。 |
| 原键 K、载荷 P′ | 先遇到命令指纹冲突，409 idempotency_key_reused；不会走到来源比较。 |

规范化会整理首尾空白、无业务顺序的集合、十进制金额表示和 UTC 微秒时间。跨账户观察可属于另一客户的有效账户；主告警的 CustomerId 与 AccountId 则必须有正确所有权。三字母大写币种校验只是格式检查，不宣称维护了完整有效币种名录。

**常见误区**：给每次 HTTP 重投换键不能代替来源事件去重；反过来，来源编号唯一也不能证明原 HTTP 响应是否成功。

本轮截图案例通过真实摄入接口创建，使用合成观察，把检测时间设在最后一笔观察之后一分钟；它用于讲解调查工作流，不是上游检测算法的实验。

### 练习与本章小结

<!-- page -->

**练习**

1. 什么信息应作为来源事件身份？为何只比较客户和金额不够？
2. 网络超时后，上游无法判断服务是否提交。如何让重试安全？
3. 如果相同外部告警编号的第二个请求更改了风险分数，应返回成功还是冲突？说明理由。

**参考解**

1. 使用规范化后的 SourceSystem 与 ExternalAlertId；不同来源可以用相同编号。客户与金额可能在许多真实事件中重复，不能代替事件身份。
2. 保留原 UUID 键、命令和载荷重试。若原事务已提交则回放；若未提交则重新执行。同一个来源事件换新键仍受业务唯一性保护。
3. 返回 409 external_alert_payload_conflict。新分数改变了原始观察内容，不是等价重投。不能覆盖原告警或悄悄再开一案；应由上游澄清来源事件。

**小结**：告警入口保留来源语义，通过验证、唯一约束、事务和幂等回执处理重复投递。外部标识冲突必须显式暴露。
