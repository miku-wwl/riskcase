# 13｜输入验证与资源授权

### 验证和授权不是同一件事

验证回答“这个请求格式与范围是否可接受”，例如评估理由不能为空、页大小不能超过 100。授权回答“这个用户能否对这条案件执行该动作”，例如只有主管可提交最终决定。

角色是粗粒度入口，领域资源规则还要检查案件是否分配给当前分析员、案件是否处在正确状态。一个格式正确的请求仍可能不被授权或不符合业务状态。

### 写入防线分层

[figure: 13-request-guardrails.svg]

认证确认请求者身份；API policy 限制 endpoint 角色；MediatR 授权行为约束命令；handler 校验负责人和版本；领域对象检查生命周期。数据库唯一索引与并发 token 把最终写入竞争变成明确冲突。

### 实时查询当前角色与锁定状态

[source: backend/RiskCase.Infrastructure/Identity/IdentityService.cs#public async Task<bool> IsInRoleAsync|6]

命令上的 `Authorize` 特性声明角色需求。应用行为通过 IIdentityService 进入这个 Infrastructure 实现，查询当前用户、锁定状态与角色；不满足就拒绝，旧 Cookie 中的角色声明不能覆盖当前数据库事实。读取同样需要 CaseReaders 角色，注册成功不自动取得业务角色。

### 当前角色、案件权限与历史回放

<!-- page -->

分析员、高级分析员和主管可以读取全案；审计员同样可读，但不能写。普通调查写入还要求当前经办人；主管可在允许的阶段转派或退回，最终处置则另受历史评估作者的独立性限制。新注册用户没有业务角色，不能因成功登录就取得案件访问权。

Cookie 声明可能早于角色撤销。MediatR 因此在进入幂等行为前查询 Identity 当前角色与锁定状态，历史回执不会绕过这一层。分派目标也通过同一 Application 抽象验证资格。CSRF 请求令牌、角色、资源关系与幂等键各有用途，不能互相替代。

| 当前身份 | 服务器允许的资源与动作 |
|---|---|
| RiskAnalyst / SeniorAnalyst | 读取全案；领取未分派案件；对自己经办的调查阶段写事实、评估与提交；撤回自己的复核提交须说明原因。 |
| RiskSupervisor | 读取全案；在非复核/非终态转派给合格用户；可经办调查，也可有理由退回；最终决定必须满足历史独立性。 |
| RiskAuditor | 读取全案；任何业务写入均拒绝。AssignedToMe 只是查询筛选，不是读取授权边界。 |
| 无业务角色 / 匿名 | 已注册登录也不自动获得案件权限；匿名无会话。两者都不能借旧键取得受保护案件结果。 |

### 练习与本章小结

<!-- page -->

**练习**

1. 将“理由不能为空”与“当前用户是主管”分别归入验证或授权。
2. 分析员读取另一经办人的案件与修改该案件，权限判断有什么不同？
3. 说明 CSRF、角色策略、`If-Match` 和幂等键分别保护什么。

**参考解**

1. 理由非空是输入验证；当前主管资格是授权；本人曾评估过该案属于领域独立性规则。有效字符串并不意味着动作被允许。
2. 读取他人案件符合 CaseReaders 全案读取策略；尝试修改则要有调查角色、当前经办关系和可编辑状态。先区分读写，不能把 AssignedToMe 筛选误当安全边界。
3. CSRF 保护浏览器请求来源；角色约束可用动作；If-Match 防止基于过时版本的新写入；幂等键恢复同一历史意图。四者各有输入和失败语义。

**小结**：输入有效不代表操作被授权。角色、资源规则、状态不变量与数据库约束共同保护写路径。
