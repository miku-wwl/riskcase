# 05｜RiskCase 生命周期与不变量

### 第 1 页｜提交复核是冻结一份调查基础

分析员在调查阶段增加笔记、建立关系并作风险评估。主管随后看到的必须是这份已经确认的调查基础。如果进入 Reviewing 后仍能补写事实，主管读过的评估与最终决定所依据的资料就可能不一致。

RiskCase 采用 New → Investigating → Reviewing → Resolved。调查阶段允许修改；复核阶段冻结事实、评估和分派。经办人或主管可以显式退回调查。Resolved 是本系统内的只读终态，不提供重开命令。

### 第 2 页｜状态转换同时约束写入边界

[figure: 05-case-lifecycle.svg]

图中的返回箭头不是撤销历史，而是开始新的调查基础。增加笔记、关系、重新分派或退回都会清除当前评估投影与当前复核引用，历史评估仍保留。经办人必须针对新的事实再次评估，才能重新提交。

评估本身也推进案件版本，但不会改变它所评估的 BasisVersion。一个版本标识写入顺序，另一个版本指出评估所依据的调查基础，二者不能混用。

### 第 3 页｜领域方法固定复核对象

[source: backend/RiskCase.Domain/Entities/RiskCase.cs#public void RequestReview|12]

RequestReview 要求当前经办人在调查阶段已经生成有效评估。提交时固定 ReviewedAssessmentId、提交人和时间，再把状态改为 Reviewing。恢复调查会使这份当前提交失效；历史审计仍记录原提交引用。

API 的 If-Match 与 EF 并发令牌确保“提交复核”和“追加事实”从同一版本出发时，最多只有一个请求成功。

### 第 4 页｜有理由的退回才是可执行的反馈

[figure: round3-review-return-loop.svg]

主管发现受益人所有权缺少证据时，应说明具体缺口。原因去除首尾空白后须有 20 至 1500 个 Unicode 字符；经办人主动撤回自己的复核提交也遵守相同规则。领域先验证状态与原因，再推进版本、清除当前评估及提交引用，历史评估不会删除。

这个闭环只改变本系统调查状态。最终的升级、监测、误报关闭或 AML 转交仍进入 Resolved；下游执行属于其他团队，不能把结案记录当作外部动作已完成。

### 第 5 页｜预测一次竞争写入

**练习**

1. 评估后又追加一条笔记，为何即使风险等级不变也应重新确认评估？
2. 版本 8 同时收到“提交复核”和“追加关系”，允许两者都成功会破坏什么承诺？
3. 为什么退回调查保留历史评估，却清除当前评估引用？

**小结**：状态控制允许的业务动作；调查基础标识评估对象；版本保护竞争写入；终态与外部后续流程的边界必须清楚。
