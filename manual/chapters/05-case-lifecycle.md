# 05｜RiskCase 生命周期与不变量

### 第 1 页｜状态是业务承诺

如果案件只是一个可随意改写的 `status` 字段，分析员可能跳过调查直接关闭，或在结案后悄悄覆盖结论。RiskCase 将状态变化集中在领域方法中，让每个变化具备允许条件、责任人和版本递增。

主路径是 New → Investigating → Reviewing → Resolved。Reviewing 状态可以因显式原因回到调查；已解决案件保持不可修改。

### 第 2 页｜状态转换图

[figure: 05-case-lifecycle.svg]

图中的箭头代表可以执行的命令，不是任意状态赋值。Reviewing 到 Investigating 是重新调查的受控路径；Resolved 是终态。这样 API 或 UI 的新增入口也必须遵守同一套业务约束。

### 第 3 页｜状态规则位于领域对象

[source: backend/RiskCase.Domain/Entities/RiskCase.cs#public void RequestReview|38]

开始调查要求合适的当前状态和负责人；请求复核要求已有结构化评估；提交处置要求正在等待复核，并且复核人不能等于被分配分析员。遇到违规状态，领域对象抛出明确规则异常，由 API 转成可读的问题响应。

### 第 4 页｜版本把状态变化变成可见事实

每次业务写入增加 `Version`，审计事件记录该版本。两个页面都显示版本 5 时，若其中一个先提交，另一个旧页面用版本 5 写入就应得到 412。它必须刷新并重新核对，而不能悄悄覆盖刚才的判断。

版本不是时间戳，也不是审计历史的替代。它是并发写入的条件令牌；审计事件解释“谁在何时做了什么”。

### 第 5 页｜练习与本章小结

**练习**

1. 为什么不能只在 React 按钮里阻止已结案操作？
2. 重新打开案件为何需要显式原因？
3. 同一时间两个用户看到 `Reviewing`，其中一个提交后，另一个应该怎样处理？

**小结**：生命周期规则集中在领域实体。版本冲突拒绝过期写入；终态保护和明确重开理由维护决策完整性。
