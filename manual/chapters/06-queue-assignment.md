# 06｜分析员队列与分派

### 第 1 页｜工作队列是待办视图

分析员的第一任务是找出当前要调查的案件，而不是阅读一张装饰性仪表盘。队列支持状态、类别、严重度、搜索、是否分派给自己和分页。严重程度按 Critical、High、Medium、Low 进行显式排序，避免把字符串顺序当业务顺序。

分析员和高级分析员可认领未分派案件；主管可以将非复核、非结案案件转派给有调查资格的有效用户，包括主管。不存在、锁定或无调查角色的目标会被服务器拒绝，且案件与审计均不改变。审计员可读全案，不能写入。

### 第 2 页｜分派与可见性

[figure: 06-queue-assignment.svg]

队列查询确定“看哪些数据”，资源授权确定“能对当前档案做什么”。两者不要合并成隐藏按钮：即使有人手工构造 HTTP 请求，服务端仍需验证角色和负责人规则。

### 第 3 页｜查询的过滤与排序

[source: backend/RiskCase.Application/RiskCases/RiskCaseQueries.cs#public async Task<RiskCaseQueuePage> Handle|34]

查询在数据库端应用过滤、排序和 `Skip/Take`，只将当前页投影为列表视图。分页参数有上下限，排序使用明确的严重级别权重，再以时间和案件 ID 确定稳定顺序。未定义的数字枚举筛选返回 400。这样大量历史案件不会在 API 内存中全部加载。

### 第 4 页｜从真实队列继续工作

[screenshot: risk-alert-queue.png]

队列一行需要同时显示来源告警、客户、类别、严重度、负责人、状态和更新时间。点击一行进入工作区后，页面读取完整案件视图；搜索和筛选只影响查询条件，不会改变服务器数据。

### 第 5 页｜练习与本章小结

**练习**

1. 为什么应该在 PostgreSQL 上分页，而不是先加载全部案件再由浏览器切页？
2. 严重度枚举值排序与字符串排序有什么差别？
3. 主管能分派案件、审计员只能读取。怎样在 UI 与 API 两边落实权限？

**小结**：队列是可筛选的服务器查询。授权仍由后端执行；角色与负责人规则共同决定具体写权限。
