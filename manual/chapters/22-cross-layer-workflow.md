# 22｜分析员完整工作流

### 沿同一案件追踪一次调查

高风险告警进入队列后，分析员登录并打开案件，核对客户、账户、交易和信号；开始调查、记录笔记、添加关联并提交评估；主管复核理由和审计历史，最后记录升级处置。

工作流有一条稳定的案件 ID 和递增版本，贯穿 API、数据库、界面、审计和测试。每个页面都应解释用户现在在哪一步、下一步需要什么权限。

### 端到端调用路径

[figure: 22-analyst-workflow.svg]

身份由 Cookie 建立；浏览器取 CSRF token；队列和案件读取经 Application 查询；写入以版本和幂等键提交；PostgreSQL 事务保存实体与审计；成功响应按服务器版本协调缓存并重新读取；草稿按编辑代次清理。主管使用独立会话核对已冻结评估并执行最终决定。

### 前端命令的边界

<!-- page -->

[source: frontend/src/pages/case-detail-page.tsx#const action = useMutation|23]

页面通过 API adapter 发起 mutation，成功后仅在结果版本更高时替换同案缓存；同版本保留已有 mutation 视图，触发重新读取，并有条件清理所捕获代次的草稿。页面保留用户输入、待处理状态和错误提示；业务结果仍由 API 响应确认。

### 沿退回闭环重新确认调查依据

<!-- page -->

[screenshot: round4/assessment-history.png]

图中第二次评估与第一次同时保留，新的复核提交明确引用第二次记录。主管先说明缺失证据，经办人按反馈补充调查、重新评估，再提交独立复核。退回不是把旧评估的理由原地覆盖，也不是让主管自己修改分析员的事实。

真实浏览器场景还延迟退回响应、模拟提交成功后响应丢失、刷新后沿用原键恢复。观察到的状态变化与审计反馈相符；这些交互结果仍需数据库级原子性和约束测试共同支持。

### 练习与本章小结

<!-- page -->

**练习**

1. 为这条工作流标出每次读 API 与写 API。
2. 哪些步骤由分析员完成，哪些由主管完成？
3. 服务器接受写入后响应丢失，前端如何恢复已确认结果？

**参考解**

1. 队列 GET /api/cases，详情 GET /api/cases/{id}；分派、开始、笔记、关系、复核、退回、决定均 POST；评估使用 PUT。每次新写入携带各自键和当前 If-Match。
2. 当前经办人调查、追加事实、评估并提交；经办人或主管可有理由退回。只有未参加本案历史评估且符合其他独立性条件的主管才能最终决定。
3. 刷新后读取该用户/案件在 sessionStorage 的原请求，再沿原键、正文和版本重放。成功回执后协调缓存并 GET 当前状态；不能把新键当作未知结果的重试。

**小结**：完整价值来自跨层一致流程，而非孤立页面。每个状态变化都在 UI、API、领域、数据库和审计中留下相互匹配的结果。
