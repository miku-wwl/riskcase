# 24｜跨层故障恢复与工程取舍

### 可靠性来自适当的边界

RiskCase 没有微服务、消息队列、机器学习平台或资金账本。它以单体 ASP.NET Core 应用和 PostgreSQL 完成一个明确业务边界。简单拓扑减少运行负担；一致性通过领域规则、事务、并发版本、幂等、权限和测试保障。

选择越少不等于深度越浅。关键是能说明每个机制解决的真实失败模式及其尚未覆盖的范围。

### 故障恢复决策

[figure: 24-failure-recovery.svg]

遇到响应超时，复用同一幂等意图重试；遇到 412，读取新版本并让人重新判断；遇到 409，按错误 code 区分重复关系、状态冲突和幂等键误用；遇到 403，确认角色和资源关系。不同故障需要不同恢复动作，不能统一“再试一次”。

### 明确当前实现的范围

<!-- page -->

这是可运行的工程样例，不是金融机构的生产认证。真实部署仍需组织管理的用户生命周期、密钥保管、TLS 与反向代理、备份和恢复演练、审计保留策略、运行监控、威胁建模以及适用法律与合规评估。示例数据与开发账号不能用于生产。

本系统的升级、监测、AML 转交只是结束本次调查的处置记录，下游执行不在系统内。幂等回执保存响应 JSON，当前实现没有自动清理过期回执；部署方要结合请求量、保留要求和敏感字段评估存储治理。此外，历史身份确实缺失的案件没有自动解除结案限制的功能；需保留未知并核实原始资料。完整历史与交易尚未分页，巨型案件仍会增加响应和图谱成本。这些已知边界不能以本机测试通过替代部署评估。

### 练习与全书回顾

<!-- page -->

**练习**

1. 分别为未知结果、并发版本冲突和权限拒绝选择恢复策略。
2. 什么时候引入异步消息基础设施才有明确理由？
3. 为一个真实银行部署列出必须在本样例之外补足的三个控制。

**参考解**

1. 未知结果保留原意图同键恢复；412 先读新版本并让人重新判断；403 核查当前角色和资源资格。401/403 也可能发生于原操作已提交之后的恢复阶段，不能据此推断首次提交失败。
2. 当出现独立下游职责、明确异步交付语义和失败补偿要求时再讨论消息系统。仅为显得企业化而加队列，不会自动解决当前原子性或独立复核问题。
3. 例如：组织用户与密钥生命周期；可演练的备份恢复及审计保留；部署边界的TLS、监测与适用合规评估。这些需要部署证据，不能把教材样例测试当作生产认证。

**全书回顾**：RiskCase 以真实业务边界为起点，从可解释告警走到可追溯决定。领域规则定义允许行为，PostgreSQL 事务与版本保护一致性，生成客户端和可靠草稿支持前端协作，测试与 CI 为端到端工作流提供可复核证据。
