# 20｜TanStack Query 与本地草稿同步

### 相同文本可能承载较新的意图

分析员写下 A 并保存，在请求途中把草稿改为 B，又改回 A。较早请求成功时，如果只比较字符串，当前文本与提交值相等，草稿就会被清空。但用户已经作过两次新编辑，早先的回调没有权利抹掉这些意图。

RiskCase 为每次编辑生成新的 revision，并在提交时捕获不可变 DraftSnapshot。服务器案件版本描述已确认业务事实；草稿 revision 描述本地编辑代次；二者保护不同状态。

图中 A/r1 与 A/r3 内容相同，身份不同。提交 M1 只能清理它捕获的 r1。后来的 r3 应继续留在输入框。保存成功后再次主动提交同样文本，是新的业务意图，可以产生新的笔记和幂等键。

### 清理必须同时满足本地与持久化代次

[source: frontend/src/lib/drafts.ts#const clearIfUnchanged|13]

清理先核对用户/案件/字段键与当前 revision，再检查 localStorage 的持久化 revision。另一个标签页可能已经保存新编辑，即使当前组件没有收到它的输入事件，也不能删除它。清理只写入该代次的确认标记，不改写共享草稿值；即使另一标签页在检查之后更新记录，新值也不会被旧回调覆盖。

### 同版本的当前读取也需要协调

<!-- page -->

**已知**：在用户 U、案件 C、字段 note 上，文本 A 的代次为 r1，案件缓存为 v8。M1 捕获 r1、正文 A、预期版本 8；r1/r2/r3 是便于阅读的代号，真实实现用 UUID。

| 时刻 | 本地与服务器如何变化 |
|---|---|
| t1 提交 M1 | 待恢复意图在 sessionStorage 先持久化；服务器提交笔记到 v9。 |
| t2 继续编辑 B，再回 A | 每次 setValue 生成新 revision，当前为 r3；文本相同不能使代次回到 r1。 |
| t3 M1 成功返回 | newestCase 以 Version 协调；清理检查 r1 ≠ r3，保留草稿 A。 |
| t4 另一响应带来 v10，旧 v9 再到 | mutation 不覆盖较新缓存；随后 GET 当前状态。草稿所有权独立于这些版本。 |

跨标签页还要检查持久化 revision。清理仅写入该代次的确认标志；这不是共享存储上的原子 CAS，却能避免旧回调覆盖另一个标签页新值。账号/案件切换以不同 key 和组件身份隔离。

**常见误区**：当前 GET 允许同版本元数据更新，历史 mutation 在同版本保留现有缓存；只用同一个 >= 比较会让迁移恢复的作者信息长期停留在旧投影。

### 把时间顺序变成可验证条件

<!-- page -->

**练习**

1. A → B → A 为什么不能只靠字符串比较？
2. 两个标签页共享 localStorage，旧回调清理前还要核对什么？
3. v8 响应晚于 v9 返回，案件缓存与本地输入分别应怎样处理？

**参考解**

1. r1 的 A 与 r3 的 A 值相同但代次不同。请求捕获 r1，回调看到当前 r3 就必须保留 A；比较文本会错误地抹掉两次编辑。
2. 还须核对用户/案件/字段键、本地 revision 及共享持久化 revision。只给捕获代次写确认标志，不覆盖另一个标签页的新草稿。
3. 案件缓存保留 v9，随后重新读取确认；本地输入保留当前代次。即使旧请求保存成功，只要用户后来编辑过，旧完成回调就无权清空草稿。

**小结**：编辑代次保护用户意图，服务器版本保护确认事实，身份键隔离工作区，持久化原请求保护未知提交的恢复。
