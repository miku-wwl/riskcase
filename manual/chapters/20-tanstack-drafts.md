# 20｜TanStack Query 与本地草稿同步

### 第 1 页｜相同文本可能承载较新的意图

分析员写下 A 并保存，在请求途中把草稿改为 B，又改回 A。较早请求成功时，如果只比较字符串，当前文本与提交值相等，草稿就会被清空。但用户已经作过两次新编辑，早先的回调没有权利抹掉这些意图。

RiskCase 为每次编辑生成新的 revision，并在提交时捕获不可变 DraftSnapshot。服务器案件版本描述已确认业务事实；草稿 revision 描述本地编辑代次；二者保护不同状态。

### 第 3 页｜清理必须同时满足本地与持久化代次

[source: frontend/src/lib/drafts.ts#const clearIfUnchanged|14]

清理先核对用户/案件/字段键与当前 revision，再检查 localStorage 的持久化 revision。另一个标签页可能已经保存新编辑，即使当前组件没有收到它的输入事件，也不能删除它。清理只写入该代次的确认标记，不改写共享草稿值；即使另一标签页在检查之后更新记录，新值也不会被旧回调覆盖。

### 第 4 页｜缓存、草稿与请求各自拥有生命期

工作区按用户与案件重新挂载；草稿键包含这两个身份。案件缓存也包含用户 ID，收到乱序响应时按 Version 选择较新数据。成功 mutation 触发重新读取，而不是把历史回放当作当前权威快照。

未知写入的原请求保存在当前标签页 sessionStorage；草稿保存在 localStorage。刷新后恢复原幂等键，同时保留未确认清理的草稿。账户变化会清空查询工作区并重新建立会话，旧用户的迟到回调不能写入新用户缓存。这些场景已通过真实浏览器与 PostgreSQL 的定向回归。

### 第 5 页｜把时间顺序变成可验证条件

**练习**

1. A → B → A 为什么不能只靠字符串比较？
2. 两个标签页共享 localStorage，旧回调清理前还要核对什么？
3. v8 响应晚于 v9 返回，案件缓存与本地输入分别应怎样处理？

**小结**：编辑代次保护用户意图，服务器版本保护确认事实，身份键隔离工作区，持久化原请求保护未知提交的恢复。
