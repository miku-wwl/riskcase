# 20｜TanStack Query 与本地草稿同步

### 第 1 页｜服务器状态不等于输入框状态

案件事实、交易和审计历史由服务器管理，适合 TanStack Query 缓存与失效；当前筛选条件、对话框和输入光标属于组件状态；未提交的调查笔记属于用户草稿；正在发送的请求属于 pending 状态。

将它们混在一份 `useState` 对象里，会让刷新、重试或迟到响应覆盖用户输入。

### 第 2 页｜四种状态并列存在

[figure: 20-react-state-boundaries.svg]

服务器确认内容经 Query 缓存进入页面；草稿按用户和案件保存在浏览器；mutation 显示提交中与错误；成功后刷新服务端状态。用户编辑时，较旧响应不得把更新的输入覆盖掉。

### 第 3 页｜draft hook 的保护条件

[source: frontend/src/lib/drafts.ts#export function useDraft|24]

草稿存储使用用户 ID 和案件 ID 组成键。保存成功时只清除本次已提交内容；如果提交期间用户又改过字，新的草稿保留。服务端响应更新 Query cache，但输入值不会盲目重置。

### 第 4 页｜迟到成功响应的竞态

分析员写下草稿 A，点击保存；网络请求仍在进行时又补充草稿 B。服务器最终确认 A。正确行为是把 A 放入已保存笔记列表，同时保留输入框中的 B。Playwright 回归测试通过延迟请求观察了这一点。

退出或刷新后，草稿按身份与案件恢复；切换账号时键不同，避免另一位用户看到前一人的未提交内容。草稿保留策略仍应遵从组织终端隐私要求。

### 第 5 页｜练习与本章小结

**练习**

1. 交易历史适合放本地状态还是 Query cache？为什么？
2. 如何证明响应 A 没有覆盖较新的输入 B？
3. 同一浏览器切换用户时，草稿键需要哪些维度？

**小结**：服务器确认状态、组件交互、本地草稿和待处理 mutation 各自有不同生命期。成功响应要以草稿快照为条件清理。
