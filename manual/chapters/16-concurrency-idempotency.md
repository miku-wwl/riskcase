# 16｜乐观并发与幂等重试

### 第 1 页｜历史成功与当前许可是两件事

A 的笔记在版本 N 成功提交，但响应丢失。主管随后把案件转派给 B，版本变为 N+1。A 重试原意图时，需要知道当时的笔记是否保存；这不意味着 A 还可以再增加一条笔记，也不意味着版本 N 仍是当前状态。

RiskCase 的读者角色可以查看全案。只要 A 仍有当前有效的调查角色，原用户范围内的历史成功可恢复；如果角色已撤销或账户锁定，回执不能绕过服务器授权。

### 第 2 页｜回放后仍要确认当前状态

[figure: 16-concurrency-and-idempotency.svg]

服务器在幂等行为之前检查当前身份角色。相同用户、相同键、相同命令指纹回放原快照；新键仍经过 Handler 的当前负责人、版本和状态检查。前端按案件 Version 保留较新缓存，并在回放成功后重新读取当前案件。

### 第 3 页｜命令类型也属于一次业务意图

[source: backend/RiskCase.Application/Common/Behaviours/IdempotencyBehaviour.cs#public static string Fingerprint|9]

Start、Review、Resume 可能具有完全相同的 CaseId 和 ExpectedVersion。如果指纹只有字段内容，误用同一个键可能把一种命令的结果冒充另一种。指纹因此包括命令类型，同时排除传输幂等键本身。不同类型或内容复用旧键返回 409。

### 第 4 页｜丢响应、刷新与安全恢复

浏览器在发送前把账号、案件、操作、原请求体、原预期版本与 UUID 键存入当前标签页的 sessionStorage。网络失败或刷新不会把这次未知结果变成一个新操作。恢复按钮重放原始请求；成功后刷新当前服务器状态，保留尚未确认清理的用户草稿。

在旧结果尚未确认时，客户端拒绝发送同案的另一种写入意图。已明确拒绝的 400、409、412、428 可以结束该失败意图；401、403 或网络问题不能被当作原操作未提交的证明。旧版回执没有命令类型，兼容恢复须同时核对原指纹、案件、后继版本和响应审计中的原操作。能证明是原命令才回放，否则返回冲突并引导读取；原始回执不删除、不补造。

### 第 5 页｜恢复语义的推理练习

**练习**

1. A 被转派后，回放成功为什么不等于有权新增写入？
2. 回放得到 v12，缓存已有 v14，页面应保留哪个版本？
3. 为什么刷新后重试不能换一个新键或更新原 If-Match？

**小结**：历史结果解决未知提交，当前授权保护访问，案件版本保护新写入，单调缓存和重新读取保护当前视图。
