# 16｜乐观并发与幂等重试

### 第 1 页｜并发冲突与网络重试是两种问题

两个分析员从版本 12 打开案件，分别提交不同笔记，这是并发写入：过期版本必须被拒绝。一个分析员只提交一次，但 HTTP 响应丢失，这是未知结果：客户端不知道服务器是否已经提交，应使用同一个幂等键重试。

乐观并发避免静默覆盖；幂等回放避免一次意图重复生效。不能用一个机制替代另一个。

### 第 2 页｜条件写入与安全重试

[figure: 16-concurrency-and-idempotency.svg]

请求携带 `If-Match` 版本与 `Idempotency-Key`。版本匹配时数据库写入；版本过旧返回 412。相同幂等键、相同指纹会回放原响应；相同键却代表不同载荷返回 409。用户刷新后确认新事实，再以新意图产生新键。

### 第 3 页｜幂等键为何不进入请求指纹

[source: backend/RiskCase.Application/Common/Behaviours/IdempotencyBehaviour.cs#public Task<TResponse> Handle|33]

行为先校验 UUID 格式，再计算命令指纹并交给幂等存储。指纹排除幂等键本身，因此同一业务命令可在不同传输尝试中保持相同内容。用户 ID 与键共同形成范围，避免两个不同用户的键彼此冲突。

### 第 4 页｜响应丢失后的恢复推演

浏览器生成键 K，发送高风险评估。服务器保存评估、审计事件和 K 对应响应并提交；代理丢掉返回包。TanStack Query 显示未知失败时，用户重试相同待处理意图，客户端保留 K；服务器发现同指纹回执并返回已保存结果，不再新增一次评估。

若用户编辑了不同理由，不能复用 K。客户端生成新键，但仍必须提交当前 `If-Match` 版本；若旧响应已经推进版本，先重新读取再由用户确认。

### 第 5 页｜练习与本章小结

**练习**

1. 响应丢失后如何区分安全重试与全新写入？
2. 同一个键搭配不同理由为何返回冲突？
3. 如果两个请求使用不同幂等键、却编辑同一案件，哪个机制拒绝旧写？

**小结**：未知 HTTP 结果靠幂等回执恢复；并发冲突靠版本保护。重试键必须随一次用户意图固定，内容变化就应产生新的意图。
